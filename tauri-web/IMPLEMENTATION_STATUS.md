# وضعیت پیاده‌سازی نبض — شاخه `tauri-web-prototype`

آخرین بررسی: 2026-10-28

## تصمیم طراحی
- نسخهٔ دسکتاپ مرجع طراحی است؛ ظاهر فعلی دسکتاپ بدون نیاز مشخص تغییر نکند.
- نسخهٔ موبایل فعلی صرفاً پیش‌نمایش است و معیار پذیرش UI نیست.
- پیاده‌سازی در `tauri-web/` انجام می‌شود تا برنامهٔ قدیمی Rust/egui دست‌نخورده بماند.

## آنچه اکنون واقعاً کار می‌کند
- رابط Tauri 2 + Vite + TypeScript ساخته می‌شود.
- هشت صفحهٔ اصلی و جابه‌جایی بین آن‌ها وجود دارد: داشبورد، طرف‌حساب‌ها، فاکتورها، دریافت و پرداخت، کالا و انبار، گزارش‌ها، چاپ و بارکد، تنظیمات.
- جست‌وجوی محلی در فهرست‌های نمونه و میان‌برهای اولیهٔ صفحه‌کلید پیاده شده‌اند.
- SQLite محلی در مسیر AppLocalData برنامه با ساخت خودکار جدول‌ها فعال شده است؛ داده‌ها با بستن برنامه پاک نمی‌شوند.
- فرمان‌های Tauri برای ثبت و خواندن طرف‌حساب، کالا، فاکتور، دریافت/پرداخت و تنظیمات اضافه شده‌اند.
- ثبت فاکتور در تراکنش SQLite انجام می‌شود؛ خرید موجودی را افزایش می‌دهد، فروش در صورت شناسایی کالا موجودی را کاهش می‌دهد و فروش با موجودی ناکافی رد می‌شود.
- دریافت/پرداخت به‌صورت FIFO به ماندهٔ فاکتورهای باز همان طرف‌حساب تخصیص داده می‌شود.
- فرم‌های طرف‌حساب، کالا، فاکتور و دریافت/پرداخت به فرمان‌های ذخیره‌سازی متصل شده‌اند؛ فهرست‌های طرف‌حساب، فاکتور و دریافت/پرداخت و کارت‌های داشبورد دادهٔ SQLite را می‌خوانند.
- تنظیمات فروشگاه/تقویم/واحد پول و کاغذ چاپ در SQLite ذخیره می‌شوند.
- پیش‌نمایش برچسب بارکد و فراخوانی چاپ مرورگر وجود دارد؛ تولید بارکد واقعی، چاپ مستقیم و اتصال به سخت‌افزار پیاده نشده است.
- workflow پیش‌نمایش GitHub Pages و build فرانت‌اند موفق بوده‌اند.

## آنچه هنوز نمایشی یا ناقص است
- نمودار فروش هنوز نمونه‌ای است؛ برخی نماهای گزارش و فهرست کالا هنوز کامل از SQLite تغذیه نمی‌شوند.
- ویرایش و حذف رکوردها هنوز پیاده نشده‌اند؛ فاکتور فعلاً یک ردیف کالا/خدمت می‌پذیرد.
- ماندهٔ افتتاحیه و مبالغ مازاد بر فاکتورهای باز به تطبیق حساب کامل نیاز دارند؛ پیش از استفادهٔ حسابداری رسمی باید سناریوهای مالی آزمون شوند.
- گزارش‌ها از تراکنش واقعی محاسبه نمی‌شوند؛ بازهٔ نمودار فقط متن عدد را عوض می‌کند.
- تنظیمات فروشگاه و تنظیمات چاپ ذخیرهٔ دائمی ندارند.
- پشتیبان‌گیری/بازیابی واقعی، بارکد قابل اسکن، اسکنر USB-HID و چاپگرها متصل نیستند.
- تاریخ فعلی در کد ثابت است و تقویم شمسی پویا نیست.
- آزمون خودکار برای جریان‌های رابط و منطق حسابداری در این بخش وجود ندارد.

## برنامهٔ اجرا با اولویت
- [x] **مرحله ۱ — SQLite و لایهٔ داده:** تعریف schema برای طرف‌حساب‌ها، کالاها، فاکتورها، ردیف فاکتور، دریافت/پرداخت و تنظیمات؛ افزودن فرمان‌های Tauri برای خواندن/نوشتن.
- [ ] **مرحله ۲ — اتصال فهرست‌ها:** حذف داده‌های hard-coded و خواندن اطلاعات واقعی از SQLite؛ جست‌وجو، حالت خالی و خطا.
- [ ] **مرحله ۳ — فرم‌های ذخیره‌شونده:** ثبت طرف‌حساب و کالا با اعتبارسنجی و پیام واقعی پیاده شده؛ ویرایش/حذف هنوز باقی است.
- [ ] **مرحله ۴ — گردش حسابداری:** فاکتور تک‌ردیفی، جمع/تخفیف، کنترل موجودی و تخصیص FIFO دریافت/پرداخت پیاده شده؛ فاکتور چندردیفی و آزمون‌های جامع باقی است.
- [ ] **مرحله ۵ — گزارش‌های محاسباتی:** محاسبهٔ فروش، دریافت، مانده و ارزش موجودی از پایگاه داده.
- [ ] **مرحله ۶ — تنظیمات و پشتیبان‌گیری:** ذخیرهٔ دائمی تنظیمات و export/import کنترل‌شدهٔ پایگاه داده.
- [ ] **مرحله ۷ — چاپ و بارکد:** خروجی چاپ فاکتور و برچسب، تولید بارکد واقعی و سپس آزمایش سخت‌افزار.
- [ ] **مرحله ۸ — آزمون و انتشار:** آزمون‌های Rust و TypeScript، بررسی سناریوهای حسابداری، ساخت AppImage و deb روی CI و حفظ سازگاری مانجارو.

## معیار پذیرش
1. بعد از بستن و باز کردن برنامه، رکوردهای ذخیره‌شده باقی بمانند.
2. ثبت فاکتور موجودی و مانده را مطابق قواعد مشخص و به‌صورت اتمیک تغییر دهد.
3. جمع گزارش‌ها با رکوردهای SQLite قابل تطبیق باشد.
4. خطاهای ذخیره‌سازی به‌جای پیام موفقیت نمایشی به کاربر نشان داده شوند.
5. ظاهر دسکتاپ تأییدشده بدون تغییر غیرضروری حفظ شود.
