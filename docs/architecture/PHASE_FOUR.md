# فاز چهار — داشبورد و گزارش‌های مالی/عملیاتی

**وضعیت پیاده‌سازی و CI:** تکمیل و تأییدشده در شاخهٔ توسعه  
**شاخه:** `ui/react-tauri-redesign`  
**مبنای داده:** SQLite محلی و دفتر ثبت Rust؛ هیچ دادهٔ نمونه‌ای در گزارش‌ها استفاده نمی‌شود.

## دامنهٔ تکمیل‌شده

- [x] داشبورد: فروش و دریافت خالص امروز، بدهی مشتریان و تأمین‌کنندگان، ارزش موجودی بر اساس میانگین بهای تمام‌شده و سود ناخالص ماه.
- [x] شاخص‌های ماه جاری: فروش، خرید، سود خالص و تعداد کالاهای کم‌موجود.
- [x] گزارش دوره‌ای فروش، خرید، دریافت و پرداخت با تاریخ شمسی و فیلتر طرف‌حساب.
- [x] گزارش برگشت فروش و مرجوعی خرید بر اساس تاریخ واقعی برگشت؛ جمع برگشت‌ها برای اطلاع جدا نمایش داده می‌شود و دوباره از مبلغ فاکتورِ قبلاً اصلاح‌شده کسر نمی‌شود.
- [x] سود ناخالص از فروش خالص فاکتور و snapshot بهای تمام‌شدهٔ ردیف‌های باقی‌مانده؛ برگشت‌ها مقدار COGS را کاهش می‌دهند.
- [x] هزینه‌های عملیاتی، سود خالص و هشدار فروش فاقد snapshot بهای تمام‌شدهٔ تاریخی در گزارش و داشبورد.
- [x] روند روزانهٔ فروش با روزهای بدون فروش و فهرست ۱۰ کالای پرفروش بر اساس تعداد خالص پس از برگشت.
- [x] بدهی فعلی مشتریان/تأمین‌کنندگان، ارزش موجودی و هشدار کم‌موجودی.
- [x] خروجی CSV فارسی با BOM، کوتیشن استاندارد و محافظت در برابر Formula Injection.
- [x] اعتبارسنجی تاریخ واقعی، ترتیب بازه و محدودیت ۳۶۶ روز؛ تست فیلتر طرف‌حساب، برگشت، COGS، هزینه و بازهٔ خالی/نامعتبر.
- [x] فیلتر طرف‌حساب فقط گزارش‌های وابسته به طرف‌حساب را محدود می‌کند؛ هزینه و ارزش موجودی به‌درستی عمومی باقی می‌مانند.

## قواعد تفسیر گزارش

- فروش/خرید بر اساس تاریخ فاکتور و مبلغ جاری سند پس از برگشت‌های ثبت‌شده گزارش می‌شود.
- مبلغ برگشت جداگانه بر اساس تاریخ برگشت نمایش داده می‌شود؛ نباید بار دیگر از جمع فروش/خرید کسر شود، چون هسته قبلاً مبلغ فاکتور را اصلاح کرده است.
- COGS فقط از `unit_cost` تاریخی ردیف فاکتور محاسبه می‌شود؛ قیمت خرید فعلی جایگزین سابقهٔ گمشده نمی‌شود.
- اگر فروش کالای فاقد snapshot بهای تاریخی وجود داشته باشد، هشدار داده می‌شود و سود ناخالص «کامل» تلقی نمی‌شود.
- هزینه‌ها و ارزش موجودی داده‌های کل فروشگاه‌اند و با انتخاب طرف‌حساب فیلتر نمی‌شوند.
