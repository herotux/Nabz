# فاز سه — فاکتور و فروش سریع

**شاخه:** `ui/react-tauri-redesign`  
**وضعیت:** در حال اجرا؛ این سند فقط موارد واقعاً پیاده‌شده را تیک می‌زند.

## هدف

تکمیل مسیر روزمره ثبت فاکتور فروش و خرید با حفظ قواعد حسابداری فاز یک و کاتالوگ/موجودی فاز دو. رابط نباید خودش محاسبات مالی را مرجع نهایی بداند؛ اعتبارسنجی و ثبت نهایی همچنان در Rust/SQLite انجام می‌شود.

## پیاده‌سازی انجام‌شده در این گام

- [x] نمایش زنده جمع ردیف‌ها، تخفیف، مبلغ نهایی، دریافت فعلی و ماندهٔ فروش در فرم فاکتور.
- [x] اعتبارسنجی سمت رابط برای خالی نبودن ردیف‌ها، تعداد صحیح مثبت، قیمت صحیح نامنفی و تخفیف معتبر پیش از ارسال.
- [x] جلوگیری از حذف آخرین ردیف فاکتور؛ هر فاکتور باید حداقل یک ردیف قابل ویرایش داشته باشد.
- [x] انتخاب روش دریافت فروش (نقدی، کارت‌خوان، انتقال بانکی) در کنار وضعیت تسویه.
- [x] نمایش راهنمای صریح برای ثبت پرداخت خرید از بخش دریافت/پرداخت؛ هسته فعلی عمداً پرداخت نقدی خرید را داخل فرمان فاکتور نمی‌پذیرد.
- [x] جایگزینی عملیات حذف فاکتور در جدول با فرمان `void_invoice`؛ ابطال فقط با تأیید کاربر و با حفظ سابقه انجام می‌شود و محدودیت‌های امن هسته رعایت می‌شوند.

## موارد باز فاز سه

- [ ] پیش‌نویس/تعلیق فاکتور و ادامهٔ آن پس از بستن فرم؛ نیازمند جدول draft نسخه‌بندی‌شده و بازیابی امن است.
- [ ] تجربهٔ ثبت دریافت/پرداخت هم‌زمان با فاکتور خرید، با تخصیص شفاف به همان فاکتور و بدون دور زدن دفتر پرداخت.
- [ ] رابط برگشت جزئی فروش و مرجوعی خرید با انتخاب ردیف‌های همان فاکتور، سقف مقدار قابل برگشت و نمایش مبلغ بازپرداخت/اعتبار.
- [ ] صفحهٔ جزئیات فاکتور شامل ردیف‌ها، پرداخت‌ها، تخصیص اعتبار، برگشت‌ها و وضعیت ابطال.
- [ ] جلوگیری قطعی از ارسال تکراری یک فرم در سطح backend با کلید idempotency؛ disabled شدن دکمه به‌تنهایی تضمین کافی نیست.
- [ ] شماره‌گذاری/جست‌وجو و فیلتر فاکتورها بر اساس نوع، تاریخ و وضعیت تسویه.
- [ ] تست خودکار مسیرهای جدید و بررسی اجرای کامل CI روی آخرین head.

## معیار پذیرش

1. فاکتور فروش چندردیفی با کالا و خدمت معتبر ثبت شود؛ خدمت موجودی را تغییر ندهد.
2. فروش نقدی گذری فقط با تسویه کامل مجاز باشد؛ فروش نسیه/جزئی به مشتری ثبت‌شده نیاز داشته باشد.
3. تخفیف از مبلغ ناخالص بیشتر نشود و مبلغ نهایی در UI با مقدار ذخیره‌شده در SQLite برابر باشد.
4. خرید موجودی و حساب تأمین‌کننده را طبق قواعد هسته به‌روزرسانی کند؛ پرداخت خرید از مسیر ثبت پرداخت تخصیص‌پذیر باشد.
5. ابطال، برگشت و مرجوعی سوابق مالی و انبار را حذف نکنند و عملیات ناسازگار را متوقف کنند.
6. CI شامل تست Rust/SQLite، build فرانت‌اند و ساخت بستهٔ Arch روی آخرین commit سبز باشد.
