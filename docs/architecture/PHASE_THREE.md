# فاز سه — تکمیل چرخهٔ فاکتور و فروش

**وضعیت پیاده‌سازی:** تکمیل‌شده  
**شاخه:** `ui/react-tauri-redesign`  
**آخرین commit کد تأییدشده:** `4a97946da13cde4e7511923bba49879b385fda14`

## دامنه

تکمیل چرخهٔ فاکتور فروش و خرید با تکیه بر هستهٔ حسابداری Rust/SQLite فاز یک و کاتالوگ/موجودی فاز دو. رابط فقط پیش‌نمایش و ورودی می‌دهد؛ اعتبارسنجی نهایی، تخصیص مالی، تغییر موجودی و ثبت سابقه در backend انجام می‌شود.

## موارد تکمیل‌شده

- [x] نمایش زندهٔ جمع ردیف‌ها، تخفیف، مبلغ نهایی، مبلغ مبنای تسویه و مانده در فرم فاکتور.
- [x] اعتبارسنجی تعداد صحیح مثبت، قیمت صحیح نامنفی، ردیف غیرخالی و تخفیف معتبر؛ جلوگیری از حذف آخرین ردیف.
- [x] انتخاب روش دریافت فروش: نقدی، کارت‌خوان و انتقال بانکی.
- [x] پیش‌نویس پایدار فاکتور فروش/خرید در SQLite؛ ذخیره، به‌روزرسانی، ادامه و حذف پیش‌نویس.
- [x] حفظ پیش‌نویس‌ها و کلیدهای idempotency در پشتیبان JSON v2 و بازیابی سازگار پشتیبان‌های قبلی.
- [x] جزئیات فاکتور با اقلام، پرداخت‌های تخصیص‌یافته، اعتبار اعمال‌شده، برگشت‌ها، بازپرداخت‌ها و سابقهٔ ابطال.
- [x] ثبت دریافت/پرداخت مستقیم روی همان فاکتور انتخاب‌شده؛ محدودیت مبلغ به ماندهٔ واقعی و ثبت allocation در همان تراکنش.
- [x] برگشت جزئی فروش و مرجوعی خرید از رابط؛ کنترل سقف مقدار برگشتی در UI و backend، محاسبهٔ اعتبار/بازپرداخت و حفظ سوابق.
- [x] هدف‌گیری ردیف برگشت با شناسهٔ داخلی `invoice_item_id`؛ چند ردیف تکراری از یک کالا در یک فاکتور بدون ابهام قابل برگشت‌اند.
- [x] ابطال امن فاکتور از فهرست و جزئیات؛ سابقه حذف نمی‌شود و قواعد هسته جلوی ابطال ناسازگار را می‌گیرند.
- [x] idempotency سمت backend برای ثبت فاکتور با کلید یکتا در دیتابیس؛ ارسال مجدد همان درخواست، موجودی و دفتر مالی را دوباره تغییر نمی‌دهد.
- [x] جلوگیری از ارسال سریع تکراری در فرم فاکتور و فرم پرداخت.
- [x] جست‌وجو و فیلتر فاکتورها بر اساس شماره/متن، نوع، وضعیت تسویه و بازهٔ تاریخ شمسی.
- [x] migration نسخهٔ ۱۳ برای جدول پیش‌نویس‌ها و کلید یکتای idempotency؛ داده‌های فاکتورهای قبلی حفظ می‌شوند.

## معیارهای پذیرش

1. [x] فاکتور چندردیفی فروش/خرید با قواعد موجودی، خدمت، تخفیف و طرف‌حساب هسته ثبت می‌شود.
2. [x] فروش گذری فقط در حالت تسویهٔ کامل مجاز است؛ فروش نسیه/جزئی به مشتری ثبت‌شده نیاز دارد.
3. [x] پرداخت خرید و فروش به فاکتور انتخاب‌شده تخصیص می‌یابد و مبلغ بیشتر از مانده پذیرفته نمی‌شود.
4. [x] برگشت جزئی/مرجوعی از مقدار باقی‌مانده بیشتر نمی‌شود و اثر موجودی و حساب به‌صورت تراکنشی ثبت می‌شود.
5. [x] ابطال و برگشت سوابق را حذف نمی‌کنند و عملیات ناسازگار را متوقف می‌کنند.
6. [x] تست‌های هسته، تست یکپارچگی Tauri، TypeScript، build باینری و بستهٔ Arch/Manjaro موفق شدند.
