# فاز یک — دیتابیس و هستهٔ حسابداری

**وضعیت:** پیاده‌سازی backend در شاخهٔ `ui/react-tauri-redesign` انجام شده و تست‌های CI موفق‌اند. این سند وضعیت کد را از تأیید نصب روی دستگاه واقعی جدا می‌کند.

## معماری فعال

`React / TypeScript → Tauri 2 commands → nabz-core → SQLite`

- crate مستقل `crates/nabz-core` منبع اصلی قواعد مالی، migration و عملیات دیتابیس است.
- `tauri-web/src-tauri/src/lib.rs` فقط adapter فرمان‌های Tauri و لایهٔ سازگاری UI است.
- مسیر دیتابیس نسخهٔ Tauri تغییر نکرده: `~/.local/share/com.herotux.nabz.webprototype/nabz.sqlite3`.
- شناسهٔ برنامه عمداً `com.herotux.nabz.webprototype` باقی مانده تا نصب آزمایشی دیتابیس تازه‌ای نسازد.

## schema نسخهٔ ۸

| نسخه | تغییر |
|---|---|
| 1 | وضعیت ابطال فاکتور و ساختار برگشت فروش/بازپرداخت |
| 2 | برگشت خرید و بازپرداخت تأمین‌کننده |
| 3 | دفتر ثبت اصلاح موجودی |
| 4 | محافظت از سابقهٔ اصلاح موجودی در برابر ویرایش/حذف |
| 5 | snapshot بهای خرید هر ردیف و جدول هزینه‌ها |
| 6 | میانگین بهای تمام‌شدهٔ موجودی |
| 7 | اعتبار مشتری/تأمین‌کننده، اعتبار مصرف‌شده در فاکتور، snapshotهای موجودی و شاخص‌ها |
| 8 | snapshot قیمت خرید پیش از فاکتور برای ابطال دقیق |

- هر ارتقای schema روی دیتابیس موجود، قبل از تغییر ساختار یک SQLite backup می‌سازد.
- foreign keys و WAL فعال‌اند و عملیات چندمرحله‌ای در transaction اجرا می‌شوند.
- migration روی دیتابیس قدیمی Tauri با دادهٔ موجود تست شده و ماندهٔ اعتباری، تعداد کالا و فاکتورهای قبلی را حفظ می‌کند.

## قواعد حسابداری پیاده‌شده

- میانگین موزون متحرک هنگام خرید و برگشت خرید محاسبه می‌شود.
- بهای تمام‌شده در لحظهٔ فروش روی هر ردیف فاکتور ذخیره می‌شود؛ خریدهای بعدی سود تاریخی را تغییر نمی‌دهند.
- خدمت با پیشوند «خدمت:» موجودی و بهای کالایی ایجاد نمی‌کند.
- دریافت/پرداخت ابتدا ماندهٔ افتتاحیه و سپس بدهی فاکتورها را به ترتیب FIFO تسویه می‌کند.
- اضافه‌دریافت مشتری و اضافه‌پرداخت تأمین‌کننده به اعتبار مستقل تبدیل می‌شود و در فاکتور بعدی قابل مصرف است.
- فروش گذری فقط با تسویهٔ کامل مجاز است؛ فروش اعتباری/جزئی به مشتری ثبت‌شده نیاز دارد.
- برگشت فروش، موجودی و بهای تاریخی را اصلاح می‌کند؛ برگشت خرید، بهای تاریخی کالای خارج‌شده را از ارزش موجودی کم می‌کند.
- ابطال فاکتور حذف فیزیکی نیست. فقط وقتی گردش بعدی، برگشت، اصلاح موجودی یا تغییر بهای ناسازگار وجود نداشته باشد، با عملیات معکوس و حفظ سابقه انجام می‌شود.
- اصلاح موجودی با علت ثبت می‌شود و رکوردهای آن immutable هستند.
- ثبت هزینه و گزارش سود/زیان، بهای کالای فروش‌رفته و ردیف‌های بدون بهای تاریخی را جدا می‌کند.

## پشتیبان‌گیری و بازیابی

- فرمت JSON جدید `nabz-backup-v2` است و کالا، طرف‌حساب، فاکتور، ردیف‌ها، دریافت/پرداخت، تنظیمات، برگشت‌ها، بازپرداخت‌ها، اصلاح موجودی و هزینه‌ها را نگه می‌دارد.
- فایل‌های `nabz-backup-v1` قدیمی همچنان قابل اعتبارسنجی و بازیابی‌اند؛ داده‌های جدیدِ غایب در نسخهٔ قدیمی مقدار پیش‌فرض امن می‌گیرند.
- پیش از restore از دیتابیس فعلی SQLite backup ایمنی ساخته می‌شود.
- اعتبارسنجی ساختار و جمع ردیف‌ها قبل از تغییر انجام می‌شود؛ بازیابی در transaction انجام شده و foreign-key check و integrity check پیش از commit اجرا می‌شوند.

## سازگاری با داده‌های قدیمی

- دیتابیس فعلی Tauri در همان مسیر نگه داشته و به schema v8 ارتقا داده می‌شود.
- برای کالاهای قدیمی، چون تاریخچهٔ لایه‌های خرید کامل نیست، `average_cost` اولیه از `buy_price` فعلی مقداردهی می‌شود؛ این یک **برآورد افتتاحیه** است، نه بازسازی میانگین تاریخی.
- ردیف‌های فروش قدیمی که snapshot بهای تمام‌شده ندارند، عمداً با بهای ساختگی پر نمی‌شوند و در گزارش به‌عنوان فروش بدون بهای تاریخی شمرده می‌شوند. برگشت/ابطال خودکار چنین فاکتورهایی تا تکمیل اطلاعات لازم متوقف می‌شود.
- دیتابیس egui قدیمی در `~/.local/share/nabz/nabz.sqlite3` دست‌نخورده و جدا باقی می‌ماند. انتقال خودکار آن انجام نشده؛ تا زمانی که نگاشت مانده‌ها و پرداخت‌های قدیمی تأیید نشده، ادغام خودکار می‌تواند ماندهٔ مالی را دوباره‌شماری کند.
