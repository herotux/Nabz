# فاز یک — دیتابیس و هستهٔ حسابداری

**وضعیت کد:** پیاده‌سازی backend روی شاخهٔ `ui/react-tauri-redesign` انجام شده است.  
**وضعیت آزمون آخرین تغییرات:** در انتظار اجرای موفق CI روی آخرین commit.  
**وضعیت دستگاه واقعی:** نصب و آزمون روی Manjaro واقعی هنوز انجام نشده است.

## معماری فعال

`React / TypeScript → Tauri 2 commands → nabz-core → SQLite`

- `crates/nabz-core` منبع اصلی قواعد مالی، migration، backup و عملیات دیتابیس است.
- `tauri-web/src-tauri/src/lib.rs` adapter فرمان‌های Tauri و سازگاری با UI را نگه می‌دارد.
- مسیر canonical دیتابیس Tauri: `~/.local/share/com.herotux.nabz/nabz.sqlite3`.
- شناسهٔ پایدار برنامه `com.herotux.nabz` است؛ دیتابیس Tauri قبلی از `com.herotux.nabz.webprototype` با SQLite backup به مسیر جدید منتقل می‌شود و فایل مبدأ باقی می‌ماند.

## نسخه‌بندی schema

| نسخه | تغییر |
|---|---|
| 1 | وضعیت ابطال فاکتور و ساختار برگشت فروش/بازپرداخت |
| 2 | برگشت خرید و بازپرداخت تأمین‌کننده |
| 3 | دفتر ثبت اصلاح موجودی |
| 4 | محافظت از سابقهٔ اصلاح موجودی در برابر ویرایش/حذف |
| 5 | snapshot بهای خرید هر ردیف و جدول هزینه‌ها |
| 6 | میانگین بهای تمام‌شدهٔ موجودی |
| 7 | اعتبار مشتری/تأمین‌کننده، اعتبار مصرف‌شده در فاکتور، snapshotهای موجودی و شاخص‌ها |
| 8 | snapshot قیمت خرید پیش از فاکتور برای ابطال دقیق |
| 9 | دفتر مستقل ابطال فاکتور با مبلغ برگشت نقدی و اعتبار برگشتی |
| 10 | دفتر تخصیص دریافت/پرداخت به فاکتور، ماندهٔ افتتاحیه و پیش‌پرداخت |
| 11 | اطلاعات تکمیلی کاتالوگ کالا، خدمت و شاخص‌های موجودی |

- هر ارتقای schema روی دیتابیس موجود، قبل از تغییر ساختار SQLite backup می‌سازد.
- foreign keys، WAL، شاخص‌ها و transactionهای عملیات مالی فعال‌اند.
- migration نسخه‌های قبلی Tauri به v11 بدون حذف جدول‌های قبلی انجام می‌شود.
- تخصیص‌هایی که قبل از v10 ثبت شده‌اند قابل بازسازی قطعی نیستند؛ آن‌ها جعل یا حدس زده نمی‌شوند. تخصیص‌های جدید به‌صورت رویداد مستقل ثبت می‌شوند.

## قواعد حسابداری پیاده‌شده

- میانگین موزون متحرک هنگام خرید و برگشت خرید محاسبه می‌شود.
- بهای تمام‌شده در لحظهٔ فروش روی هر ردیف فاکتور ذخیره می‌شود؛ خریدهای بعدی سود تاریخی را تغییر نمی‌دهند.
- خدمت با پیشوند «خدمت:» موجودی و بهای کالایی ایجاد نمی‌کند.
- دریافت/پرداخت ابتدا ماندهٔ افتتاحیه و سپس بدهی فاکتورها را به ترتیب FIFO تسویه می‌کند.
- اضافه‌دریافت مشتری و اضافه‌پرداخت تأمین‌کننده به اعتبار مستقل تبدیل می‌شود و در فاکتور بعدی قابل مصرف است.
- هر دریافت/پرداخت جدید، تخصیص خود به فاکتور، ماندهٔ افتتاحیه یا اعتبار را در `payment_allocations` ثبت می‌کند.
- فروش گذری فقط با تسویهٔ کامل مجاز است؛ فروش اعتباری/جزئی به مشتری ثبت‌شده نیاز دارد.
- برگشت فروش، موجودی و بهای تاریخی را اصلاح می‌کند؛ برگشت خرید، بهای تاریخی کالای خارج‌شده را از ارزش موجودی کم می‌کند.
- بازپرداخت‌های فروش و خرید به‌عنوان گردش جدا ثبت می‌شوند و گزارش وجه نقد، دریافتی/پرداختی خالص را نشان می‌دهد.
- ابطال فاکتور حذف فیزیکی نیست. فقط وقتی گردش بعدی، برگشت، اصلاح موجودی یا تغییر بهای ناسازگار وجود نداشته باشد، با عملیات معکوس و ثبت در `invoice_voids` انجام می‌شود. ردیف دریافت اولیه حذف نمی‌شود.
- اصلاح موجودی با علت ثبت می‌شود و رکوردهای آن immutable هستند.
- ثبت هزینه و گزارش سود/زیان، بهای کالای فروش‌رفته و ردیف‌های بدون بهای تاریخی را جدا می‌کند.
- گردش حساب طرف‌حساب، تخصیص‌ها، برگشت‌ها، بازپرداخت‌ها و ابطال‌ها را در خروجی backend جداگانه ارائه می‌کند.

## مهاجرت مسیر دیتابیس و دیتابیس قدیمی egui

شناسهٔ پایدار برنامه `com.herotux.nabz` است و مسیر پیش‌فرض Linux برابر `~/.local/share/com.herotux.nabz/nabz.sqlite3` است.

- اگر دیتابیس Tauri prototype در `~/.local/share/com.herotux.nabz.webprototype/nabz.sqlite3` وجود داشته باشد و مقصد جدید وجود نداشته باشد، با SQLite backup به مسیر پایدار منتقل می‌شود. فایل prototype حذف یا تغییر داده نمی‌شود و schema مقصد بعد از کپی تا v11 ارتقا می‌یابد.
- اگر هر دو دیتابیس prototype و egui وجود داشته باشند، دیتابیس Tauri اولویت دارد؛ import egui اجرا نمی‌شود و هیچ دو دیتابیسی با هم ادغام نمی‌شوند.

مسیر قدیمی egui: `~/.local/share/nabz/nabz.sqlite3`.

مهاجرت خودکار egui فقط در شرایط زیر اجرا می‌شود:

1. فایل دیتابیس قدیمی وجود داشته باشد و integrity check آن موفق باشد.
2. دیتابیس Tauri هیچ کالا، طرف‌حساب، فاکتور، پرداخت، هزینه یا تنظیم ذخیره‌شده‌ای نداشته باشد.
3. مسیر دیتابیس با `NABZ_DB_PATH` به‌صورت دستی override نشده باشد.

پیش از import، از فایل egui یک SQLite backup در پوشهٔ `backups` کنار دیتابیس Tauri ساخته می‌شود. سپس در یک transaction اطلاعات پشتیبانی‌شده منتقل می‌شود:

- کالاها، کد/SKU، بارکد، قیمت‌ها و موجودی فعلی
- طرف‌حساب‌ها و مانده‌های قابل‌تفسیر
- فاکتورهای فروش و ردیف‌ها
- فاکتورهای خرید، تأمین‌کننده و پرداخت ثبت‌شده
- هزینه‌های فروشگاه
- گردش‌های دستی انبار که با گردش فروش/خرید دوباره‌شماری نمی‌شوند

فایل egui هرگز حذف یا بازنویسی نمی‌شود. تراکنش‌های حسابداری شخصیِ غیرمرتبط با فروشگاه نیز در فایل قدیمی باقی می‌مانند و وارد دفتر فروشگاه نمی‌شوند.

**محدودیت‌های import:**

- نسخهٔ قدیمی برای فروش، وضعیت دریافت یا روش پرداخت جداگانه نداشت؛ فروش‌های قدیمی به‌عنوان فروش نقدی تسویه‌شده منتقل می‌شوند و این فرض در یادداشت هر دریافت ثبت می‌شود.
- schema قدیمی فقط `purchase_price` جاری را داشت؛ میانگین بهای افتتاحیه از آن برآورد می‌شود و در شمار هشدارهای مهاجرت قرار می‌گیرد.
- برای فروش‌های قدیمی فاقد `sale_item_costs` بهای تمام‌شده ساخته نمی‌شود؛ آن‌ها بدون COGS باقی می‌مانند.
- اگر دیتابیس مقصد داده داشته باشد، هیچ merge خودکاری انجام نمی‌شود. در صورت ناسازگاری نقش طرف‌حساب یا دادهٔ خراب، transaction لغو می‌شود و فایل مبدأ دست‌نخورده می‌ماند.

## پشتیبان‌گیری و بازیابی

- فرمت JSON `nabz-backup-v2` کالا، طرف‌حساب، فاکتور، ردیف‌ها، دریافت/پرداخت، تخصیص‌ها، ابطال‌ها، تنظیمات، برگشت‌ها، بازپرداخت‌ها، اصلاح موجودی و هزینه‌ها را نگه می‌دارد.
- فایل‌های `nabz-backup-v1` و v2 قدیمی همچنان قابل اعتبارسنجی و بازیابی‌اند؛ آرایه‌های جدید در فایل‌های قدیمی اختیاری‌اند.
- پیش از restore از دیتابیس فعلی SQLite backup ایمنی ساخته می‌شود.
- اعتبارسنجی ساختار، شناسه‌ها، ارجاع‌های خارجی و جمع ردیف‌ها قبل از commit انجام می‌شود؛ بازیابی در transaction اجرا شده و foreign-key check و integrity check دارد.

## تست و شواهد

تست‌های جدیدی برای موارد زیر به کد اضافه شده‌اند:

- مهاجرت v8 به v11 و حفظ داده‌های موجود
- import غیرمخرب دیتابیس egui، نگهداری فایل اصلی و جلوگیری از import تکراری/merge
- تخصیص FIFO دریافت‌ها، ماندهٔ افتتاحیه و پیش‌پرداخت
- حفظ دریافت نقدی و ثبت دفتر ابطال به‌جای حذف پرداخت
- گزارش دریافتی/پرداختی خالص پس از برگشت و ابطال
- اعتبارسنجی backup شامل allocation و void records

آخرین اجرای CI روی commit `5468465` نشان داد ۵۱ تست از ۵۴ تست core موفق‌اند و سه تست فقط به‌دلیل انتظار اشتباه نسخهٔ schema برابر ۱۰ شکست می‌خورند؛ schema واقعی اکنون v11 است. این انتظارها اصلاح شده‌اند و اجرای مجدد CI در جریان است.
