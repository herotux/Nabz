# تصمیم‌های معماری نبض

آخرین بازبینی: 2026-11-17

## تصمیم قطعی

نسخهٔ اصلی و فعال نبض از این پشته استفاده می‌کند:

- رابط: React + TypeScript + Vite
- پوستهٔ دسکتاپ: Tauri 2
- منطق و دسترسی به داده: Rust
- پایگاه داده: SQLite محلی
- بستهٔ رسمی لینوکس: بستهٔ بومی Arch/Manjaro با پسوند `.pkg.tar.zst`

شاخهٔ مرجع توسعه در این مرحله `ui/react-tauri-redesign` و PR مرجع شمارهٔ ۸ است. این انتخاب به معنی ادغام یا انتشار فوری نیست؛ `main` تا عبور از آزمون‌های پذیرش دست‌نخورده می‌ماند.

## گزینه‌هایی که دیگر مسیر فعال نیستند

- Slint: از محصول نهایی حذف شده است؛ رابط دوم یا امکان تعویض رابط ساخته نمی‌شود.
- egui: رابط قدیمی و کد ریشهٔ مخزن فقط تا پایان بررسی مهاجرت داده و بازبینی تاریخی نگه داشته می‌شود؛ خروجی انتشار جدید از آن ساخته نمی‌شود.
- خروجی‌های AppImage، Flatpak و deb: مسیر انتشار نبض نیستند. گردش‌کارهای قدیمی آن‌ها در شاخهٔ مرجع غیرفعال شده‌اند.
- وب مستقل: فعلاً هدف انتشار نیست؛ رابط React داخل پوستهٔ Tauri و با فرمان‌های Rust اجرا می‌شود.

## قواعد داده و شناسهٔ برنامه

- شناسهٔ فعلی Tauri برابر `com.herotux.nabz.webprototype` است.
- مسیر فعلی دیتابیس Tauri در لینوکس معمولاً `~/.local/share/com.herotux.nabz.webprototype/nabz.sqlite3` است.
- دیتابیس نسخهٔ قدیمی egui در `~/.local/share/nabz/nabz.sqlite3` مسیر جداگانه‌ای دارد.
- شناسه یا مسیر دیتابیس Tauri تا زمان پیاده‌سازی مهاجرت، تهیهٔ پشتیبان و آزمون بازیابی تغییر نمی‌کند.
- هیچ نسخه‌ای حق ندارد هنگام نصب، ارتقا یا حذف برنامه پوشهٔ دادهٔ کاربر را پاک کند.
- ادغام PR شمارهٔ ۵ یا تغییر schema بدون مهاجرت نسخه‌بندی‌شده و پشتیبان قابل‌بازیابی ممنوع است.

## استفاده از کد حسابداری PR شمارهٔ ۵

PR شمارهٔ ۵ به‌عنوان منبع انتقال انتخابی منطق مالی بررسی می‌شود، نه شاخه‌ای برای ادغام کامل. موارد ارزشمند آن:

- crate مستقل `crates/nabz-core`
- مهاجرت نسخه‌بندی‌شدهٔ SQLite تا schema نسخهٔ ۸
- میانگین موزون متحرک موجودی
- ذخیرهٔ `unit_cost` در ردیف فروش برای حفظ سود تاریخی
- برگشت فروش/خرید، ابطال، اصلاح موجودی و گزارش سود و زیان
- آزمون‌های مرتبط با مهاجرت و بهای تمام‌شده

### دلیل عدم ادغام مستقیم

در PR شمارهٔ ۸، schema در `tauri-web/src-tauri/src/lib.rs` ساخته می‌شود و هنوز مسیر مهاجرت نسخه‌بندی‌شدهٔ هسته را به‌کار نمی‌گیرد. منطق مالی و SQL نیز داخل همان فایل قرار دارد. در PR شمارهٔ ۵، schema و مهاجرت‌ها در `nabz-core` هستند و API عملیات حسابداری ساختار دیگری دارد. بنابراین انتقال صرف فایل‌ها یا ادغام کامل PR شمارهٔ ۵ می‌تواند داده و عملیات فعلی را ناسازگار کند.

مسیر درست: افزودن crate به شاخهٔ React/Tauri، تطبیق فرمان‌های Tauri با API هسته، تهیهٔ پشتیبان پیش از مهاجرت دیتابیس Tauri، آزمون دیتابیس خالی و دیتابیس دارای داده، سپس حذف SQL تکراری از لایهٔ رابط.

## قواعد شاخه و انتشار

1. توسعهٔ قابلیت‌های جدید فقط روی شاخهٔ مرجع React/Tauri انجام شود.
2. PR شمارهٔ ۸ تا پایان آزمون‌های خود Draft می‌ماند.
3. شاخه‌های Slint و بسته‌بندی دو رابط منبع ادغام نیستند.
4. `main` فقط پس از CI سبز، بازبینی تغییرات داده و آزمون نصب/اجرا روی Manjaro به‌روزرسانی می‌شود.
5. هر ادعای وضعیت باید بین «پیاده‌سازی شده»، «آزمون خودکار موفق» و «روی دستگاه واقعی تأیید شده» تفکیک شود.


## نقشهٔ دقیق انتقال از PR شمارهٔ ۵

PR شمارهٔ ۵ بر پایهٔ `feature/slint-native-ui` ساخته شده و نسبت به `main` شاخه‌ای واگراست؛ مقایسهٔ فعلی ۲۴۷ commit جلوتر و ۲۷ commit عقب‌تر از `main` را نشان می‌دهد. بنابراین merge یا cherry-pick دسته‌جمعی آن قابل‌قبول نیست.

|---|---|
| `crates/nabz-core/Cargo.toml` | انتقال و افزودن به workspace/dependency پس از بررسی مجوزها و وابستگی‌ها |
| `crates/nabz-core/src/lib.rs` | انتقال بخش مسیر داده، schema، migration، backup و restore؛ حذف enum و منطق انتخاب/تعویض Slint/Tauri |
| `crates/nabz-core/src/accounting.rs` | انتقال عملیات حسابداری و تست‌های واحد؛ تطبیق ورودی‌ها و خروجی‌ها با فرمان‌های فعلی Tauri |

| `scripts/*deb* ` و بسته‌بندی deb | به مسیر انتشار Arch منتقل نمی‌شوند؛ فقط ایده‌های آزمون حفظ داده در صورت نیاز بازنویسی می‌شوند |

### ترتیب ادغام امن هسته

1. افزودن crate بدون تغییر رفتار برنامه و اجرای تست‌های مستقل آن.
2. تبدیل schema فعلی Tauri به ورودی migration شناخته‌شده؛ پیش از هر تغییر، SQLite Online Backup و بررسی `integrity_check` انجام شود.
3. آزمون روی دیتابیس خالی، دیتابیس Tauri دارای داده و نسخهٔ کپی‌شده از دیتابیس قدیمی؛ هیچ تستی روی دیتابیس اصلی کاربر اجرا نشود.
4. انتقال یک عملیات در هر مرحله (کالا، طرف‌حساب، خرید، فروش، پرداخت، برگشت) و نگه‌داشتن API فرمان‌های Tauri به‌عنوان لایهٔ سازگاری UI.
5. حذف SQL تکراری از `tauri-web/src-tauri/src/lib.rs` فقط پس از عبور تست‌های رگرسیون همان عملیات.


## تصمیم‌های فاز یک — 2026-11-17

- `nabz-core` به‌عنوان تنها منبع قواعد مالی و دسترسی دیتابیس به Tauri متصل شد؛ رابط دوم/Slint در معماری جاری وجود ندارد.
- schema جاری ۸ است. تغییرات افزوده‌شده در v8 قیمت خرید پیش از فاکتور را snapshot می‌کند تا ابطال خرید، قیمت خرید و میانگین موجودی را دقیق برگرداند.
- migration روی دیتابیس قدیمی Tauri قبل از تغییر schema پشتیبان می‌گیرد؛ مسیر برنامه و دیتابیس عمداً تغییر نکرده‌اند.
- واردکردن خودکار دیتابیس egui ممنوع است تا نگاشت مانده‌ها و پرداخت‌های قدیمی و احتمال دوباره‌شماری بررسی و تأیید شود.
- ردیف‌های قدیمی فاقد COGS تاریخی بدون حدس‌زدن باقی می‌مانند؛ گزارش آن‌ها را جدا نشان می‌دهد.
- جزئیات و تست‌های پذیرش در [گزارش فاز یک](PHASE_ONE.md) ثبت شده‌اند.
