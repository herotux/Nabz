# تصمیم‌های معماری نبض

آخرین بازبینی: 2026-11-17

## تصمیم قطعی

نسخهٔ اصلی و فعال نبض از این پشته استفاده می‌کند:

- رابط: React + TypeScript + Vite
- پوستهٔ دسکتاپ: Tauri 2
- منطق و دسترسی به داده: Rust
- پایگاه داده: SQLite محلی
- بستهٔ رسمی لینوکس: بستهٔ بومی Arch/Manjaro با پسوند `.pkg.tar.zst`

شاخهٔ مرجع توسعه در این مرحله `ui/react-tauri-redesign` و PR مرجع شمارهٔ ۸ است. این انتخاب به معنی ادغام یا انتشار فوری نیست؛ `main` تا عبور از آزمون‌های پذیرش دست‌نخورده می‌ماند.

## گزینه‌هایی که دیگر مسیر فعال نیستند

- Slint: از محصول نهایی حذف شده است؛ رابط دوم یا امکان تعویض رابط ساخته نمی‌شود.
- egui: رابط قدیمی و کد ریشهٔ مخزن فقط تا پایان بررسی مهاجرت داده و بازبینی تاریخی نگه داشته می‌شود؛ خروجی انتشار جدید از آن ساخته نمی‌شود.
- خروجی‌های AppImage، Flatpak و deb: مسیر انتشار نبض نیستند. گردش‌کارهای قدیمی آن‌ها در شاخهٔ مرجع غیرفعال شده‌اند.
- وب مستقل: فعلاً هدف انتشار نیست؛ رابط React داخل پوستهٔ Tauri و با فرمان‌های Rust اجرا می‌شود.

## قواعد داده و شناسهٔ برنامه

- شناسهٔ فعلی Tauri برابر `com.herotux.nabz` است.
- مسیر پایدار دیتابیس Tauri در لینوکس معمولاً `~/.local/share/com.herotux.nabz/nabz.sqlite3` است.
- دیتابیس Tauri نسخهٔ prototype در `~/.local/share/com.herotux.nabz.webprototype/nabz.sqlite3` قرار داشت و در اولین اجرا با SQLite backup به مسیر پایدار منتقل می‌شود؛ فایل قبلی باقی می‌ماند.
- دیتابیس نسخهٔ قدیمی egui در `~/.local/share/nabz/nabz.sqlite3` مسیر جداگانه‌ای دارد.
- شناسهٔ برنامه به `com.herotux.nabz` تثبیت شده و انتقال دیتابیس prototype با backup و بدون حذف مبدأ پیاده‌سازی شده است؛ migration داخلی schema نسخهٔ ۱۰ نیز فعال است.
- هیچ نسخه‌ای حق ندارد هنگام نصب، ارتقا یا حذف برنامه پوشهٔ دادهٔ کاربر را پاک کند.
- ادغام PR شمارهٔ ۵ یا تغییر schema بدون مهاجرت نسخه‌بندی‌شده و پشتیبان قابل‌بازیابی ممنوع است.

## استفاده از کد حسابداری PR شمارهٔ ۵

PR شمارهٔ ۵ به‌عنوان منبع انتقال انتخابی منطق مالی بررسی می‌شود، نه شاخه‌ای برای ادغام کامل. موارد ارزشمند آن:

- crate مستقل `crates/nabz-core`
- کد اولیهٔ PR5 برای migration نسخه‌بندی‌شده (در مسیر جاری تا schema نسخهٔ ۱۰ تکمیل شده است)
- میانگین موزون متحرک موجودی
- ذخیرهٔ `unit_cost` در ردیف فروش برای حفظ سود تاریخی
- برگشت فروش/خرید، ابطال، اصلاح موجودی و گزارش سود و زیان
- آزمون‌های مرتبط با مهاجرت و بهای تمام‌شده

### دلیل عدم ادغام مستقیم

در نسخهٔ اولیهٔ PR شمارهٔ ۸، schema و SQL در `tauri-web/src-tauri/src/lib.rs` قرار داشت و migration نسخه‌بندی‌شده نداشت. در فاز یک، این وضعیت اصلاح شد: `nabz-core` به dependency مستقیم Tauri تبدیل شد و فرمان‌های Tauri به API هسته وصل شدند. PR شمارهٔ ۵ همچنان شاخه‌ای واگرا با معماری دو رابط است؛ بنابراین ادغام کامل آن یا cherry-pick دسته‌جمعی هنوز می‌تواند فایل‌ها و workflowهای نامرتبط را وارد کند.

مسیر انتخابی در فاز یک اجرا شد: افزودن crate به شاخهٔ React/Tauri، تطبیق adapterهای Tauri با API هسته، پشتیبان پیش از migration، تست دیتابیس خالی و legacy Tauri و انتقال عملیات مالی. adapterهای Tauri باقی می‌مانند؛ حذف SQL تکراری فقط در صورت وجود و پس از تست رگرسیون هر عملیات انجام می‌شود.

## قواعد شاخه و انتشار

1. توسعهٔ قابلیت‌های جدید فقط روی شاخهٔ مرجع React/Tauri انجام شود.
2. PR شمارهٔ ۸ تا پایان آزمون‌های خود Draft می‌ماند.
3. شاخه‌های Slint و بسته‌بندی دو رابط منبع ادغام نیستند.
4. `main` فقط پس از CI سبز، بازبینی تغییرات داده و آزمون نصب/اجرا روی Manjaro به‌روزرسانی می‌شود.
5. هر ادعای وضعیت باید بین «پیاده‌سازی شده»، «آزمون خودکار موفق» و «روی دستگاه واقعی تأیید شده» تفکیک شود.

## تصمیم‌های فاز یک — 2026-11-17

- `nabz-core` به‌عنوان تنها منبع قواعد مالی و دسترسی دیتابیس به Tauri متصل شد؛ رابط دوم/Slint در معماری جاری وجود ندارد.
- schema جاری ۱۰ است. v9 دفتر مستقل ابطال فاکتور و مبلغ برگشت نقدی/اعتبار را اضافه می‌کند؛ v10 تخصیص دریافت/پرداخت به فاکتور، ماندهٔ افتتاحیه و پیش‌پرداخت را به‌صورت رویداد مستقل نگه می‌دارد.
- دیتابیس Tauri قدیمی از شناسهٔ prototype به شناسهٔ پایدار منتقل می‌شود؛ سپس migration schema با backup مستقل اجرا می‌شود. اگر هر دو دیتابیس قدیمی Tauri و egui وجود داشته باشند، Tauri اولویت دارد و هیچ ادغامی با egui انجام نمی‌شود.
- واردکردن دیتابیس egui فقط در اولین اجرای نسخهٔ Tauri و فقط وقتی مقصد خالی است مجاز است؛ قبل از import از مبدأ backup گرفته می‌شود، فایل مبدأ دست‌نخورده می‌ماند و اگر نقش طرف‌حساب/ساختار ناسازگار باشد کل transaction لغو می‌شود. فروش‌های قدیمی به‌دلیل نداشتن وضعیت پرداخت به‌عنوان نقدی فرض می‌شوند و این فرض در یادداشت ثبت می‌شود.
- ردیف‌های قدیمی فاقد COGS تاریخی بدون حدس‌زدن باقی می‌مانند؛ گزارش آن‌ها را جدا نشان می‌دهد. میانگین بهای افتتاحیهٔ موجودی قدیمی از آخرین `buy_price` برآورد می‌شود و به‌عنوان مقدار تخمینی ثبت هشدار می‌گردد.
- جزئیات و تست‌های پذیرش در [گزارش فاز یک](PHASE_ONE.md) ثبت شده‌اند.
